# 可观测性与运维

## 可观测三大支柱

| 支柱 | 回答的问题 | 载体 |
|---|---|---|
| 指标（Metrics） | 系统状态好不好（RED：Rate/Errors/Duration） | 时序数据库 + 监控大盘 |
| 日志（Logging） | 具体发生了什么 | 集中日志（SLS/ELK） |
| 链路追踪（Tracing） | 一次请求跨服务的完整路径与耗时 | TraceID 串联（OpenTelemetry 标准） |

三者用统一 TraceID/资源标签关联，才能从"告警"下钻到"根因"——割裂的三件套只叫监控，不叫可观测。

## SLO 体系

- **SLI**：服务质量指标（成功率、P99 时延）
- **SLO**：内部目标（如月度成功率 99.95%）；**SLA**：对外承诺，违约有赔付
- **错误预算（Error Budget）**：1 − SLO 的可犯错额度；预算烧完就冻结变更做稳定性——SRE 平衡速度与稳定的机制
- **黄金指标**：时延、流量、错误、饱和度（USE/RED 方法）

## 告警与值班

- **告警分级**：P0 电话叫醒 / P1 即时消息 / P2 工单；每条告警必须有 owner 与 runbook，**没有行动的告警直接删**
- **on-call 与升级路径（Escalation）**：主备值班、15 分钟响应约定、超时自动升级
- **runbook**：告警到处置动作的脚本化手册；复盘产出沉淀于此（OPS-03/04/05）

## 交付与变更

- **CI/CD**：持续集成（每次提交自动构建测试）+ 持续交付（可随时发布）；流水线里自动化测试是质量闸门（OPS-02）
- **发布策略**：**滚动**（逐批替换）、**蓝绿**（双环境瞬时切换）、**灰度/金丝雀**（小流量验证逐步放量）；都有秒级回滚预案
- **IaC（基础设施即代码）**：Terraform/ROS/CloudFormation 声明式管理资源，环境可重建可审计（OPS-01）
- **变更管理**：变更窗口、审批、灰度、回滚四件套——**大多数故障由变更引入**，管住变更等于管住一半稳定性
- **混沌工程（Chaos Engineering）**：在生产/预发注入故障（杀实例、断网络、打满 CPU），验证冗余与告警真的有效
