# 阿里云 Landing Zone 深度知识

> Landing Zone 是"上云第一天的治理基线"：在业务大规模上云**之前**，把账号、身份、网络、合规、财务、自动化的底座搭好。它是 CAF 平台维度的落地物，也是所有后续 Workload 能被治理的前提。

## 1. 为什么必须有 Landing Zone

没有 Landing Zone 的典型症状（售前现场可直接询问验证）：
- 一个主账号 + N 个 RAM 用户，权限混乱，谁都能看全量资源
- 生产/测试资源混在同一账号，误删、超额、审计分不清责任主体
- 账单一个总数，分不清哪个业务花多少
- 网段随手开，IDC 互联时发现 CIDR 冲突
- 日志散在各处，出事后没有完整证据链

Landing Zone 用**多账号隔离 + 基线代码化**一次性解决：账号是治理的最小单元，隔离边界比 RAM 策略更硬。

## 2. 演进脉络（讲给客户听背景用）

| 阶段 | 形态 | 问题 |
|---|---|---|
| Landing Zone v1 | 单账号 + RAM 分组 | 隔离弱，配额/审计/费用无法按业务分 |
| Landing Zone v2 | 资源目录（RD）多账号 + 基础管控策略 | 需要自行拼装，实施门槛高 |
| **Landing Zone on Alibaba Cloud（企业级方案/云治理中心 GCC 自动化搭建）** | 官方架构 + 检查基线 + IaC 交付 | 当前推荐形态，可自动化落基线 |

对照：AWS 侧演进是 Landing Zone（方案）→ Control Tower（产品化）；阿里云对应产品化路径是资源目录 + 配置审计/云治理中心的组合，没有单一的"Control Tower 等价物"。

## 3. 六大要素与设计要点

### 3.1 账号体系（资源目录 Resource Directory）

**结构参考**：

```
资源目录（管理账号 rd-management）
├── Core 资源夹（核心业务）
│   ├── prod-xxx、uat-xxx、dev-xxx（按业务线/环境开成员账号）
│   └── shared-service（共享服务：镜像、DNS、中台）
├── Security 资源夹（安全账号：云防火墙、堡垒机、安全中心集中部署）
├── Log 资源夹（日志审计账号：ActionTrail / 操作审计、SLS 集中投递）
└── Suspended 资源夹（停用账号封存区）
```

设计规则：
- **管理账号只做管控，不放业务资源**：只跑资源目录、RD 管控、财务单元、管控策略，人员只授予管理员最小集
- **账号划分维度**：优先按"业务线 × 环境"，一个可独立核算、独立考核的业务单元一个账号；不要按项目开账号（数量爆炸）
- **委派管理员（Delegated Administrator）**：把配置审计、SLS、共享服务等可信服务的管理权从管理账号委派到专职账号，管理账号进一步减负
- 账号有默认数量配额，规划时申请提升；账号命名与费用标签规范先于开户

### 3.2 身份与权限

- **人进 RAM/IMS（统一身份管理），应用进角色**：人员账号统一在管理账号/身份中心维护，业务账号只建 RAM 角色供扮演（assume role），避免每个账号一套用户密码
- **SSO**：对接企业 IDP（AD/AAD/Okta），员工离职一键回收；禁止共享账号
- **权限基线**：
  - 管理账号：仅平台管理员；日常运维不落管理账号
  - 业务账号：开发只读 + 运维受限管理，高危权限走堡垒机/临时提权
  - 全线最小权限，禁长期明文 AccessKey（对应 WAF SEC-01）
- **管控策略（Control Policy）**：在 RD 的资源夹/账号上挂 SCP 风格的策略，预防性禁止（如禁用公网 IP 的资源夹、禁止删 FlowLog）

### 3.3 网络规划

- **骨干网用云企业网 CEN（转发路由器 TR）**：跨地域、跨账号 VPC 互通 + 混合云（物理专线/VPN）统一挂 CEN，禁止 VPC 两两对等互通的网状结构
- **CIDR 规划表**（必须有，返工成本最高的就是它）：
  - 预留足够空间：按 10 年业务增长 × 3 年弹性的容量估
  - 分段规则示例：`10.x.0.0/16` 按地域分段，第二字节按业务线，第三字节按环境；与 IDC 现网段**绝不重叠**
  - 每账号-环境一个 VPC，生产/非生产网段隔离
- **出入口收口**：公网出口统一走集中 VPC/NAT + EIP 白名单；入口统一 WAF/DDoS 防护层（对应 WAF SEC-02）
- **共享 VPC**：共享服务（如中间件、安全资源池）用共享 VPC 发 vSwitch 给业务账号，业务账号只有实例级权限，网管权在网账号

### 3.4 合规与安全基线

| 领域 | 产品 | 基线动作 |
|---|---|---|
| 配置合规 | 配置审计 Config | 挂官方**合规包**（等保 2.0、CIS 基线），持续评估 + 自动修复规则 |
| 操作审计 | 操作审计 ActionTrail | 全账号管理/数据事件投递到 Log 账号 SLS，留存 ≥ 180 天（等保要求 6 个月起） |
| 运维审计 | 堡垒机 | 所有生产 SSH/RDP 收口堡垒机，录像留存，禁直连 EIP |
| 边界防护 | 云防火墙、WAF、DDoS 防护 | 东西向/南北向流量可视与拦截，入口统一收口 |
| 主机与数据 | 云安全中心、KMS、加密 | 补丁基线、告警接入；密钥集中 KMS，云盘/OSS 静态加密（对应 SEC-03/05） |

合规映射：等保 2.0、行业监管要求直接映射到合规包 + 日志留存策略，售前给金融/政企客户时这张表是关键页。

### 3.5 财务治理（FinOps 落点）

- **财务单元（Finance Unit）**：按业务线/成本中心建树状分摊结构；账号级 + 标签级双层分摊（跨账号共享资源靠**费用标签**拆分）
- **分账账单 + 预算管理**：每月自动出账，预算超标告警到责任人；异常检测防"忘了关的按量资源"
- **优化机制**：RI/节省计划集中管理；成本周报机制（对应 WAF COST-01~04）
- 责任模型：财务定分摊规则，CCoE 定优化目标，业务 owner 对自己的账单负责

### 3.6 自动化与 IaC

- **Landing Zone 本身要代码化**：资源目录结构、管控策略、基线配置用 Terraform（alicloud provider）或 ROS 资源编排管理，环境可重建（对应 WAF OPS-01）
- **日常运维自动化**：OOS 运维编排（定时任务、批量运维、自动修复动作）+ 云助手；合规发现的问题自动派工单/自动修复
- **新账号接入流水线**：开账号 → 挂基线（日志投递、合规包、网络接入 CEN、财务单元）全自动，目标"小时级交付一个合规账号"
- 基线检查：阿里云提供 Landing Zone 基线检查能力（云治理中心 GCC / 检查清单），实施完先跑一遍基线对齐

## 4. 交付物清单（Landing Zone 咨询/实施项目）

1. **账号规划表**：账号名、归属资源夹、用途、费用归属、负责人
2. **CIDR 规划表**：地域、VPC、网段、互通关系、与 IDC 的路由
3. **权限矩阵**：角色 × 人群 × 账号范围（含管理账号特例清单）
4. **合规基线清单**：合规包选择、日志留存策略、审计范围
5. **IaC 仓库**：RD 结构 + 管控策略 + 基线模板（可交付可重建）
6. **运营手册**：开账号流程、提权流程、告警响应路径

### 两张核心表的模板

**账号规划表**（示例行按客户实际替换；要点：管理账号零业务、委派管理员、费用归属到人）：

| 账号名 | 资源夹 | 用途 | 费用归属 | Owner | 备注 |
|---|---|---|---|---|---|
| rd-management | — | 资源目录/财务单元/管控策略，不放业务资源 | 平台成本 | 平台组 | 仅平台管理员可登录 |
| ac-shared | Core | 共享服务（镜像仓/DNS/中台） | 平台分摊 | 平台组 | |
| ac-core-a-prod | Core | 业务线 A 生产 | 业务线 A | 张三 | |
| ac-core-a-uat | Core | 业务线 A 预发/测试 | 业务线 A | 张三 | |
| ac-core-b-prod | Core | 业务线 B 生产 | 业务线 B | 李四 | |
| ac-security | Security | 云防火墙/堡垒机/安全中心集中部署 | 平台成本 | 安全组 | 安全类可信服务委派管理员 |
| ac-log | Log | ActionTrail + SLS 集中日志 | 平台成本 | 平台组 | 留存 ≥180 天 |

**CIDR 规划表**（示例分段规则：第二字节按业务/环境，地域占一字节，IDC 段独立）：

| 位置 | 账号/环境 | VPC | 网段 | 互通方式 |
|---|---|---|---|---|
| cn-hangzhou | ac-core-a-prod | vpc-hz-prod | 10.10.0.0/16 | CEN |
| cn-hangzhou | ac-core-a-uat | vpc-hz-uat | 10.20.0.0/16 | CEN |
| cn-shanghai | ac-core-a-prod（多活/灾备） | vpc-sh-prod | 10.30.0.0/16 | CEN |
| IDC 现网 | — | — | 172.24.0.0/16 | CEN + 双专线/VPN 冗余 |

规划规则：容量按 10 年增长 × 弹性余量预留；云上云下网段永不重叠；生产/非生产段号段分离便于路由与 ACL 汇总；未分配号段整段保留不零切。

## 5. 实施路径（四步）

1. **评估**：现有上云状态、应用组合、合规要求（等保/行业）、IDC 网络现状
2. **设计**：六要素设计评审（重点过账号规划表 + 网段规划表两份表）
3. **实施**：IaC 搭建 → 基线检查对齐 → 试点业务账号接入验证
4. **运营**：月度基线偏差报告、季度 FinOps 复盘、策略随合规要求迭代

常见范围陷阱：客户以为 LZ 是"开几个账号"，实际核心交付是治理基线代码化；反过来，也别把 LZ 做成大而全——先把账号/日志/权限三条硬基线落地，网络和 FinOps 可分波次。
