# AWS Cloud Adoption Framework（CAF）深度知识

> CAF 是一个**业务转型框架**，不只是技术框架。它回答的是：企业如何组织人员、流程和技术，让上云真正产生业务价值。产品无关的方法论，落地到阿里云时框架照用、产品名替换。

## 1. 定位：CAF 与相邻框架的关系

| 框架 | 回答的问题 | 层级 |
|---|---|---|
| **CAF** | 上云这场转型怎么组织、怎么管？（人与流程） | 战略层 |
| **Landing Zone** | 云上环境的基础盘怎么搭？（治理基线） | 平台层 |
| **Well-Architected（WAF）** | 每个系统的技术架构对不对？（技术支柱） | Workload 层 |
| **MAP**（Migration Acceleration Program） | 迁移项目怎么拿 AWS 资助、分几步走？ | 执行项目 |
| **Migration Evaluator** | 上云前的 TCO/业务案例怎么算？ | 可行性 |

关键记忆点：**CAF 管"组织和实施"，WAF 管"架构是否正确"**。客户谈上云战略时用 CAF，谈某个系统设计评审时用 WAF，两者配合而非二选一。MAP 是基于 CAF 的具体资助与执行项目（按评估/动员/迁移三阶段发放迁移抵扣资助，需 MAP 参与伙伴配合，有迁移体量门槛）。

## 2. 六大核心维度（Six Perspectives）

新版 CAF（2022 白皮书起）将每个维度拆为**能力（Capabilities）→ 成果（Outcomes）→ 度量（KPIs）**，共 24 项能力。售前评估时按维度打分（0-5 分成熟度），输出雷达图 + 差距清单。

### 2.1 业务（Business）
- **核心问题**：云投资如何回溯到业务成果？
- **能力主题**：业务案例与价值管理、利益相关者洞察与管理、产品与投资组合管理、创新加速（数据/AI 驱动的新收入）
- **典型动作**：定义 3 年上云北极星指标；用 Cloud Value Framework 五维度算价值（见 §4）；识别"上云才可行"的新业务机会
- **常见差距**：只有 IT 的降本目标，没有业务侧 KPI；高管sponsor缺位
- **评估问题**：谁为上云业务成果负责？业务案例里的收益是测出来的还是拍的？

### 2.2 人员（People）
- **核心问题**：组织与技能能否承接转型？
- **能力主题**：变革管理与沟通、技能评估与提升/重塑（upskilling/reskilling）、组织模型调整（集中式/联邦式/混合）、云卓越中心（CCoE）建设
- **CCoE 参考结构**：
  - 云战略组（业务 + IT 高管）：定优先级、审批投资
  - 平台组：建 Landing Zone 与共享服务
  - 迁移组：按波次执行迁移
  - 创新组：云原生/数据产品孵化
  - 自动化组：IaC 模块、CI/CD 模板、护栏代码化
- **常见差距**：培训买了但没人转岗；CCoE 变成"审批部门"而不是"赋能引擎"
- **评估问题**：核心团队有没有 20% 的时间投入转型？技能矩阵有没有覆盖到运维和财务？

### 2.3 治理（Governance）
- **核心问题**：云上怎么管住风险、合规和钱？
- **能力主题**：投资组合管理、云财务管理（FinOps：可见性、优化、运营）、风险与合规管理（控制措施代码化）、指导原则与护栏（guardrails）
- **关键实践**：
  - 护栏分**预防性**（策略禁止不合规资源创建）与**检测性**（配置审计持续评估 + 自动修复）
  - FinOps 三板斧：费用标签/分账体系、预算与异常告警、优化闭环（RI/节省计划/错峰伸缩）
- **常见差距**：出事才补策略；账单月底才发现超标
- **评估问题**：有没有人能一周内回答"我们每个业务的云成本"？

### 2.4 平台（Platform）
- **核心问题**：安全可扩展的底座怎么建？
- **能力主题**：网络与连接架构、身份与访问基线、平台自动化（IaC/CI/CD）、数据架构、共享服务（目录、DNS、镜像仓）
- **落地物**：就是 **Landing Zone**（见 landing-zone 文档）——CAF 的平台维度落地出来就是一个 Landing Zone
- **评估问题**：新业务上云是"提需求等两周"还是"自己开账号随手拉资源"？（前者说明平台到位，后者说明失控）

### 2.5 安全（Security）
- **核心问题**：安全如何融入每个层面而非事后叠加？
- **能力主题**：身份与访问管理（IAM/SSO/最小权限）、威胁检测与事件响应、基础设施与应用保护、数据保护（分类分级、加密、密钥管理）、合规证明自动化
- **关键原则**：安全左移到 IaC 模板层；事件响应预案必须演练过
- **评估问题**：有没有全量资产的清单和配置基线？密钥和敏感数据的生命周期谁管？

### 2.6 运营（Operations）
- **核心问题**：云上如何持续稳定高效运行？
- **能力主题**：可观测性与监控、事件与问题管理（on-call、升级路径）、变更与发布管理（灰度/回滚）、持续改进（故障复盘文化、运行手册 runbook）、服务台与服务目录演进
- **关键转变**：运维从"管机器"转向"管平台与自动化"，人工操作用运行编排替代
- **评估问题**：最近三次故障有没有复盘产出改进项？关键系统有没有演练过恢复？

## 3. 四个采用阶段（Adoption Phases）

> 迭代循环，不是线性瀑布。每个大项目、每个波次都会再走一遍。

| 阶段 | 目标 | 关键活动 | 出口准则（何时进入下一阶段） |
|---|---|---|---|
| **评估 Assess** | 知道自己在哪里、要去哪 | CAF 六维度成熟度评估、应用组合盘点（7R 分类）、TCO 与业务案例、试点选择 | 业务案例获批；转型战略与首批试点确定 |
| **动员 Mobilize** | 把基础和团队搭起来 | Landing Zone 落地、CCoE 组建、迁移工厂与波次计划、试点 PoC 消除高风险假设 | Landing Zone 就绪；试点迁移成功并复盘 |
| **迁移与现代化 Migrate & Modernize** | 规模化搬迁并借势升级 | 波次迁移（7R）、割接与回滚演练、迁移中同步做平台化改造（容器化/托管服务替换） | 计划内应用完成迁移；运维移交并稳定运行 |
| **创新 Innovate** | 用云能力创造新价值 | 数据平台与 AI/ML 场景孵化、Serverless/事件驱动新应用、持续实验机制 | 新产品/新收入指标可度量 |

### 7R 迁移策略（评估阶段的分类工具）

| 策略 | 含义 | 适用 |
|---|---|---|
| Rehost 重新托管 | 直接搬（lift & shift） | 快速下 IDC、时间压力大 |
| Replatform 更换平台 | 小改（换托管数据库/容器化） | 性价比最高的默认选项 |
| Refactor 重构 | 云原生重写 | 核心系统、长期演进资产 |
| Repurchase 重新购买 | 换 SaaS | 邮件、CRM 等非差异化系统 |
| Retire 淘汰 | 下线 | 盘点中发现的僵尸系统（常见 10-20%） |
| Retain 保留 | 留在原地 | 合规/延迟敏感，再评估 |
| Relocate 迁移场地 | 虚拟化层整体平移（如 VMware 环境整体迁入） | 大规模 VMware 资产、不想动应用 |

售前要点：应用组合盘点后给出 7R 分布饼图，通常 Replatform 占比越高，3 年 TCO 与敏捷收益越好；纯 Rehost 的项目要提醒客户"搬完不等于转型完成"。

## 4. 价值度量：Cloud Value Framework

业务案例不要只算降本，五维度分别找 KPI：

1. **成本规避**（Cost Avoidance）：机房/硬件/人力 TCO 对比
2. **员工生产力**（Staff Productivity）： provisioning 时间、运维人效
3. **运营韧性**（Operational Resilience）：可用性、RTO/RPO 改善、事故减少
4. **业务敏捷性**（Business Agility）：上线周期、实验频率、部署频率
5. **可持续性**（Sustainability）：能耗/碳排放优化（近年新增维度）

## 5. 关键原则与常见陷阱

**原则**：
- **CCoE 驱动**：跨职能小团队作为变革引擎，连接业务与技术
- **敏捷迭代**：反对大爆炸迁移；小步快跑、每波次复盘
- **价值回溯**：每个技术决策都能回链到 KPI/OKR
- **自动化优先**：护栏、合规、部署全部代码化（IaC + CI/CD），人工操作是债务
- **实验文化**：用试点消除风险假设，用数据说服而不是用 PPT

**常见陷阱**（售前可主动提醒客户，建立专业信任）：
1. 只迁平台不改组织 → 云成本失控、影子 IT
2. Landing Zone 缺位就开迁 → 后期账号/网络返工成本极高
3. 把 CAF 当一次性咨询项目 → 转型是持续运营，不是 PPT 交付
4. 业务不参与 → 降本达成但业务价值无人认领

## 6. 售前场景速用

- **客户问"上云值不值"**：用 Migration Evaluator 思路做 TCO + 五维度价值，重点把敏捷性和韧性量化
- **客户问"要多久"**：按四阶段给路线图，明确"第一个试点生产系统上线"是动员阶段的验收锚点
- **客户问"组织怎么调"**：给 CCoE 参考结构 + 技能矩阵，提醒集中式起步、逐步联邦化
- **客户问"和 AWS 的 MAP 什么关系"**：MAP 是 AWS 基于 CAF 的迁移资助项目（三阶段资助、伙伴参与、体量门槛）；方法论是 CAF，钱是 MAP
- **落地到阿里云**：框架不变，工具链替换（评估问卷、Landing Zone 用阿里云方案、评审用阿里云 WAF，见 cross-cloud-mapping.md）

> 注意时效性：CAF 随 Serverless、FinOps、生成式 AI 持续演进（近年新增了 AI 相关考量与 lens），正式方案前核对厂商最新白皮书与行业版指南（金融、医疗等行业有补充版）。
