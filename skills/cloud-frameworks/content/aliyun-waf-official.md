## 2. 框架结构（已核实：五支柱，现行命名）

**官方框架自始至终为五支柱，无第六支柱；AI 是"延伸/Lens"而非新支柱；没有可持续性支柱（与 AWS 六支柱的最大结构差异）。**

| 时期 | 官方命名 |
|---|---|
| 2023 白皮书 | 安全合规、稳定性、成本优化、卓越运营、高效性能 |
| 2025-07 文档重构至今（现行） | **安全（Security）、稳定（Reliability）、成本（Cost Optimization）、效率（Operational Excellence）、性能（Performance Efficiency）** |

⚠️ 命名勘误：2025-07 重构后"效率"对应英文 **Operational Excellence（卓越运营）**，"性能"对应 **Performance Efficiency**——与 AWS 六支柱中文名直译（"卓越运营""性能效率"）恰好错位，写方案/对比时注意。

## 3. 落地方法论：学习 → 度量 → 优化（+ 双轨度量）

- **学习**：《云卓越架构白皮书》理论方法与设计原则。
- **度量**（[度量页](https://help.aliyun.com/document_detail/2882554.html)）：
  - 客观度量 = **云治理中心免费检测**（官方口径"260 多项检测指标"，基于实时数据自动识别风险、生成可视化评估报告、标注优先级并给修复建议）；
  - 主观度量 = **Well-Architected Tool 自助问答**（记录风险与治理进程，长期跟踪）——即 AWS Well-Architected Tool 的对应物。
- **优化**：云治理中心线上自助治理 + 场景化解决方案（100 篇）+ 阿里云服务团队/生态伙伴专家服务。
- 术语注记：**HRI/MRI（高/中风险项）源自 AWS Well-Architected Review 术语体系**，阿里云官方口径是"学习-度量-优化 + 主观/客观双轨度量"，官方页面未见 HRI/MRI 字样。本项目 `aliyun-waf` 清单沿用 HRI/MRI 属项目内约定。

## 4. 逐支柱详解（官方设计原则原文摘录）

### 4.1 安全支柱（Security）

子章节：概述 / 安全责任模型 / 云平台数据安全和隐私保障体系 / 规划和设计 / 安全设计原则 / 安全风险识别和检测 / 安全防护 / 监控和分析 / 安全响应。（[支柱索引](https://help.aliyun.com/zh/well-architected/security-compliance-1/)）

**设计原则 4 条**（[原文](https://help.aliyun.com/zh/well-architected/safety-design-principles)）：
1. **最小化原则**——"对外提供的服务越少，安全风险越小"。五个子项：网络最小化、身份最小化、权限最小化、RAM 用户权限最小化、AccessKey 权限最小化（不建议云账号下直接创建 AK，应在 RAM 用户等可控账号下申请）。
2. **审计可追溯原则**——所有来自用户端的访问请求留有审计记录，通过云资源操作日志、访问日志、变更日志还原攻击事件、追溯过程、定级定位。
3. **数据安全保护原则**——基于责任共担模型；租户侧 7 子原则：数据分类分级、访问控制和权限最小化、静态数据保护、动态数据保护（传输加密）、数据审计、数据共享、数据合规性。
4. **合规性原则**——充分考虑当地法律法规，标记满足法规的技术控制措施与管理控制措施。

### 4.2 稳定支柱（Reliability）

子章节：概述 / 设计原则 / 设计方案 / 高可用架构设计 / 变更风控 / 故障应急 / 故障管理 / 故障演练。（[支柱索引](https://help.aliyun.com/zh/well-architected/stability-1/)）

**设计原则 3 条**（[原文](https://help.aliyun.com/zh/well-architected/design-principles-3)）：
1. **面向失败的架构设计**——系统异常事件不可避免（网络延迟、硬件故障、软件错误、突峰流量），设计阶段就从"失败"出发，提供冗余、隔离、降级、弹性。
2. **面向精细的运维管控**——版本控制、灰度发布、监控告警、自动巡检等精细化可观测手段提高运维效率、确定性和稳定性。
3. **面向风险的应急快恢**——高效的故障应急流程机制 + 稳定的技术平台：实时发现、有效协同、准确记录、快速止损恢复、事后复盘。

### 4.3 成本支柱（Cost Optimization）

子章节：概述 / 设计原则 / 云上成本管理框架 / 用云计划阶段 / 用云执行阶段 / 监控分析阶段 / 成本优化阶段 / 平衡业务目标与成本。（[支柱索引](https://help.aliyun.com/zh/well-architected/cost-optimization-1/)）

**设计原则 5 条**（[原文](https://help.aliyun.com/zh/well-architected/design-principles-1)）：
1. **实施云上财务规划及管理**——成本文化、成本责任制，具备预算编制与规划、统一结算、成本可视化、成本分摊能力。
2. **衡量投入产出比（ROI）**——结合业务收益数据决策加强投入或降本。
3. **选择适合的资源及计费方式**——相比 IaaS 自建，云原生 PaaS/SaaS 通常整体成本更优。
4. **为应用负载引入弹性机制**——按最小需要申请，动态扩缩容。
5. **持续监控及优化**——成本管理是反复迭代的持续运营过程；定期检查利用率，治理闲置/低负载/高负载资源。

成本四阶段（计划→执行→监控分析→成本优化）与[云上成本管理产品地图](https://www.aliyun.com/price/cost-management)对应（预算、节省计划、抢占式实例、CDT、高额消费预警、成本分析等）。

### 4.4 效率支柱（Operational Excellence，卓越运营）

子章节：概述 / 构建运营模型 / 设计阶段 / 构建阶段 / 运营阶段。**2025-07 重构后无独立"设计原则"页**。（[支柱索引](https://help.aliyun.com/zh/well-architected/operational-excellence-1/)）

官方一句话定义："侧重于应用研发态、运行态相关自动化工具与系统的构建和使用。关键主题包括自动化更改、响应事件以及定义管理日常运营的标准。"（[门户](https://open.aliyun.com/well-architected)）

### 4.5 性能支柱（Performance Efficiency）

子章节：概述 / 高性能架构设计 / 性能测试 / 性能监控 / 性能优化。（[支柱索引](https://help.aliyun.com/zh/well-architected/efficient-performance-1/)）

官方定义："侧重于 IT 和计算资源的结构化和简化分配。关键主题包括选择针对工作负载要求优化的资源类型和大小、监视性能以及随着业务需求的发展保持效率。"

## 5. AI 卓越架构（AI Lens，2026-09-20 发布）

- **定位（原文）**："阿里云 AI 卓越架构（Well-Architected Framework AI Lens）是阿里云卓越架构框架在人工智能领域的延伸与深化，系统性地阐述了如何在阿里云平台上设计、构建、运行和持续优化 AI 工作负载，覆盖从模型选型、推理架构、数据管道到智能体编排的完整技术栈。"（[AI 时代的卓越架构](https://help.aliyun.com/zh/well-architected/excellent-architecture-in-the-ai-era)）
- **明确不是第六支柱**："并非另起炉灶，而是在五大支柱之上为 AI 工作负载补充一层专项指引。"
- 核心架构模式：大语言模型推理服务、RAG、多智能体协作、模型微调与评估、AI 数据工程；原则适用于多模态系统（Token→"推理单元"、提示词→"多模态输入编排"）。
- **AI 负载的本质差异**：传统支柱关心"资源是否充足、配置是否正确"，AI 视角进一步审视"模型是否可信、推理是否经济、智能体是否可控"——输出概率性、质量是多维光谱、成本=模型大小×上下文长度×调用频次、安全边界从网络层延伸到语义层（提示词注入）。
- **度量扩展**：除可用性/时延/吞吐量外，新增模型质量（准确率、幻觉率、一致性）、Token 经济性（单位业务价值的 Token 消耗）、护栏有效性（拦截率与误判率）、合规覆盖度（算法备案完成率、内容审核通过率）。
- **评审机制**（[行动建议](https://help.aliyun.com/document_detail/3063431.html)）：三层——①轻量自评（1-2 小时，输出各支柱得分雷达图/差距列表/改进优先级）；②AI 云治理中心自动化度量；③"主观自评+客观度量"双轨。
- 章节目录：AI 时代的卓越架构 / AI 原生转型 / AI 架构决策框架 / 安全 / 稳定 / 成本 / 效率 / 性能 / 行动建议。（[索引](https://help.aliyun.com/zh/well-architected/ai-excellence-architecture/)）
- **前史**：2025 云栖大会联合信通院发布《生成式 AI 卓越架构设计指导原则》（[电子书](https://developer.aliyun.com/ebook/8470)、[解读](https://developer.aliyun.com/article/1706331)），按五支柱给出 GenAI 专项指引（模型供应链安全、断点续训、DevOps+MLOps 一体化、GPU 算力成本、TTFT/TPS/GPU 利用率指标），可视为 AI Lens 前身。

## 11. 二轮深度补充（2026-10 第二轮调研）

### 11.1 安全支柱 28 篇最佳实践篇目（页面原文）

⚠️ 结构勘误：官方为嵌套结构（安全架构基础 → 身份和访问控制〔人员/程序/权限三子场景〕→ 基础设施防护〔纯概览，无独立篇目〕→ 计算资源防护 → 威胁检测与响应〔事件检测子场景〕），非扁平"六大场景"。

| 场景（篇数） | 篇目 |
|---|---|
| 安全架构基础（2） | 避免使用 Root 身份；对不同的工作负载进行合理隔离 |

### 11.2 四支柱子页结构（2025-07 重构版）

- **稳定**：高可用架构设计（三大基石：容灾、容错、容量）→ 变更风控（可观测/可灰度/可回滚/变更发布策略）→ 故障应急（故障基础数据管理→发现→应急协同→恢复→复盘）→ 演练。
- **成本**（12 篇）：用云计划（需求/组织/财务/资源规划）→ 用云执行（财务管理/资源管理/预算和成本管理）→ 监控分析（监控预警/成本可视化）→ 成本优化（计费方式/资源使用/持续架构优化）。
- **性能**：高性能架构设计 4 节——设计准则、评估合适的云服务、资源伸缩和系统扩展、挑战和注意事项。
- **效率**：设计阶段（设计原则/可观测性/自动化运营）→ 构建阶段（部署管理/变更管理）→ 运营阶段（事件管理等）。

### 11.4 Well-Architected Tool 使用细节

- 云治理中心内嵌的主观度量工具：创建**工作负载**（名称/描述/评审负责人/环境/标签，问卷默认"阿里云卓越架构官方问卷"）→ 逐题评估（可标不适用+原因、分次保存）→ 报告识别**高风险/中风险**问题并给治理建议 → **里程碑**保存多份评估快照跨阶段对比（问卷版本升级自动建里程碑）→ PDF 报告下载。
- 付费配套：卓越架构咨询服务（现状调研→分析建议→带优先级的改进建议→改进计划）与实施服务（一个服务包实施 2 个模块优化，按人天计）。（[WA Tool 指南](https://help.aliyun.com/zh/cgc/user-guide/well-architected-tool)）

### 11.5 检测体系与报告形态

- 双轨检测：云治理成熟度检测（传统资源）与 AI 治理成熟度检测（AI 负载，41 项）按同一五支柱独立检测、独立计分、报告分别下载。
- 检测项四元属性：分类（支柱下场景）、说明（含判定阈值，如"高危特权 RAM 身份 ≤3 个视为满足"）、快速修复说明（是否一键修复）、是否辅助决策。
- 报告：综合检测+检测详情（数据详情+治理方案）、PDF/Excel 下载、订阅推送、历史分值趋势、自动/手工修复、按"风险程度×治理难易度"分层辅助决策。

### 11.6 云网络卓越架构设计指南（最成熟的领域扩展）

四架构 × 五视角（[前言](https://help.aliyun.com/zh/cloud-network-well-architected-design/foreword)）：
1. **数据中心网络**：单 VPC 网络；同地域多 VPC（东西向安全、服务共享、统一公网出口）
2. **应用交付网络**：SLB 构建（ECS/ACK）；IDC 服务器应用交付；GA 加速广域网
3. **全球化网络**：专线混合云/多云；云上跨地域；IPsec-VPN/SD-WAN 分支上云
4. **云上网络智能运维**：NIS+云监控——告警、巡检、观测，快速定位与预防

五视角：稳定性（面向失败设计）、安全合规（DDoS/入侵/行业合规）、卓越性能（弹性随流量缩放）、可观测（"传统人工经验已难以胜任，必须采用自动化工具辅助决策"）、自服务（IaC+自动化配置的能力中心）。

### 11.7 稳定性体系深度（白皮书 + 演练产品线）

- 《云上业务稳定性保障实践白皮书》（154 页）：②理论概念（稳定性/故障）③**故障管理体系**（等级定义→故障分→全流程：发现/应急/快恢/复盘/改进追踪）④**变更管控体系**（标准流程规范；管控动作：准入/灰度/观测/回滚/数据记录上报）⑤行业实践（游戏：新游上线保障；直播：赛事直播与监控；平台网站：监控预警/全链路压测/高可用/演练预案）。
- 快恢手段六字诀：**重启、回滚、扩容、切流、限流、降级**。
- 演练产品线演化（已核实）：2016 内部 MonkeyKing → 2018 输出 **AHAS**（架构感知/应用防护/故障演练/功能开关）→ 2019 开源 **ChaosBlade**。⚠️ 退市勘误：**公有云 AHAS 故障演练模块已于 2024-11-01 正式下线**（飞天企业版 CHAOS 与 MSHA 多活容灾持续发展）——引用时注意时效。
- 演练方法论（官方文档实抓）：故障模型按 IaaS/PaaS/SaaS 分层；**有损演练**（线上真实环境、低频 1-2 月一次：多活断网/生产突袭）vs **无损演练**（全链路灰度环境常态引流 1%、每周 1-2 次：监控感知/告警响应/预案有效性）；阿里实践含机房断网演练、"全民扫雷"、生产突袭（约一年一次）。

### 11.9 效率与性能支柱要点（2025 版）

- **效率·构建运营模型**：三大基础模型——**分散式**（利于创新、跨团队沟通复杂；适合持续创新高复杂应用）、**集中式**（标准化平台、稳定低成本、权限受限；适合强管控稳态）、**CCoE 云卓越中心**（管理层定战略+CCoE 虚拟团队定供给/治理/分摊+云管理团队建运维体系；适合大规模迁移与创新驱动）；组织转型"反复迭代不断优化"。
- **性能·评估合适的云服务**：把业务指标转译为云产品性能指标（IOPS/带宽/延迟）；计算按 I/O 密集→存储增强型、网络密集→网络增强型、加速→GPU/FPGA；存储按吞吐/IOPS/延迟/可靠性（块 9 个 9、对象 12 个 9、文件 11 个 9）；网络 CEN/GA/CLB-NLB-ALB（99.995%）/NAT/Anycast EIP/CDN；数据库强调产品组合（如 Redis 缓存）。

### 11.10 解决方案精选深读（场景/方案/产品骨架）

1. **多账号操作日志统一归集与审计**（solution-37）：等保 180 天留存（操作审计默认在线仅 90 天）→ 管理账号一次配置多账号跟踪 + 强制日志投递（不可停删）→ 日志审计账号 SLS（实时分析 180 天）+ OSS（长期归档）；含 IP 归属、RAM 用户时间线、角色扮演链路追踪的 SLS SQL 样例。
2. **ECS 应用系统同城灾备**（solution-264）：云盘异步复制（EBS）跨 AZ 冷备——容灾实例平时"已停止"仅占存储；RPO 固定 15 分钟；故障时按量启动+云助手开机脚本+ALB 健康检查切流；支持独立演练环境。产品组合：HBR+ECS+ALB+VPC。
3. **多账号企业云上分账**（solution-33）：账号规划+标签打标（department/project/env）+财务单元树映射；共享资源（NAT/CEN）按平均或比例公摊；官方标注实施时长约 60 分钟。
