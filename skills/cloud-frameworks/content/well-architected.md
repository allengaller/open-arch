# Well-Architected 卓越架构框架深度知识

> WAF 回答"**这个技术架构对不对**"。CAF 管"怎么组织和实施转型"（人/流程），WAF 管"Workload 的技术质量"（架构支柱）——两者配合使用：CAF 定战略与治理，WAF 评审每一个 Workload。
>
> 本项目内逐项评审工具见 `aliyun-waf` 技能包（checklist.yaml 五支柱清单），本篇是方法论与知识底座，两包配套使用。

## 1. AWS Well-Architected 六支柱

### 1.1 卓越运营（Operational Excellence）
**定义**：以支持业务价值的运营能力运行和演进系统。

**设计原则**：用代码执行操作（IaC/运行编排）；小步可回滚的频繁变更；按预设程序演练故障；从失败中学习并持续改进（复盘文化）；运营流程即代码（runbook 可执行）。

**最佳实践**：
- 基础设施与配置全部代码化，环境可重建
- CI/CD 含自动化测试与灰度发布，变更小批量
- 统一可观测（指标/日志/链路），告警分级有升级路径
- 关键故障必复盘，产出改进项并跟踪关闭（runbook 沉淀）

**代表性服务**：CloudFormation / Systems Manager / CloudWatch / CodePipeline；阿里云对应 ROS/OOS、ARMS/SLS、云效。

### 1.2 安全性（Security）
**定义**：保护信息、系统和资产，同时用风险评估与缓解策略交付业务价值。

**设计原则**：强身份基线（最小权限、集中身份）；全层可追溯（审计日志）；全层防护（不只是边界）；传输/静态全程加密；事件响应预案化；安全自动化（代码内建护栏）。

**最佳实践**：
- RAM/IAM 最小权限 + SSO，禁长期明文 AK，高危操作走临时凭证/提权
- 入口 WAF/DDoS 收口，安全组最小开放
- KMS 集中管钥，云盘/数据库/OSS 静态加密，TLS 全链路
- ActionTrail/CloudTrail 全量审计集中留存；漏洞扫描与补丁常态化
- 事件响应：角色、升级路径、演练（tabletop exercise）

**代表性服务**：IAM/KMS/GuardDuty/Security Hub/WAF&Shield；阿里云对应 RAM/KMS/云安全中心/云防火墙/堡垒机。

### 1.3 可靠性（Reliability）
**定义**：系统从基础设施或服务故障中恢复、动态获取计算资源满足需求、缓解配置错误或瞬时中断。

**设计原则**：自动从故障恢复；故障注入测试验证恢复路径；停止猜测容量（按需水平扩展）；变更自动化管理。

**关键概念**：
- **RTO/RPO 先行**：先和业务定目标，再选方案——99.95% 与 99.99% 的方案成本差一个量级
- **多级容灾**（由低到高）：备份恢复（Backup & Restore）→ 冷备（Pilot Light）→ 热备（Warm Standby）→ 多活（Active/Active）
- 单 AZ 部署即单点：关键应用跨可用区，负载均衡 + 健康检查
- 依赖降级与熔断：下游故障不击穿自己

**代表性服务**：Route 53/Auto Scaling/ELB/AWS Backup/Elastic Disaster Recovery；阿里云对应 SLB/ESS 弹性伸缩/HBR 混合云备份/云解析 DNS。

### 1.4 性能效率（Performance Efficiency）
**定义**：高效使用计算资源满足需求，并随技术演进保持效率。

**设计原则**：新技术产品化（选托管/Serverless 而非自建）；全球部署问题几十分钟解决（Go Global 用边缘）；服务端无状态化；实验更频繁（性能测试常态化）；机械式同情——让技术选型贴近业务访问模式。

**最佳实践**：
- 容量评估有模型依据（QPS/带宽/数据增长），不拍脑袋
- 读热点：CDN + 缓存分层（本地缓存/分布式缓存）
- 数据层：读写分离、分库分表、冷热分层与数据生命周期
- 异步化削峰：消息队列解耦
- 定期基准测试/全链路压测，Graviton/倚天等新架构实例评估

**代表性服务**：CloudFront/Lambda/ElastiCache/Aurora/Graviton；阿里云对应 CDN、函数计算 FC、Tair、PolarDB、倚天实例。

### 1.5 成本优化（Cost Optimization）
**定义**：以最低价格交付业务价值的系统能力（避免超前投入）。

**设计原则**：按用量付费模式；度量整体效率；停止在非差异化高权重工作上花钱（用托管服务）；把钱花在资源而非硬件规格上（分析和归属）。

**最佳实践**：
- 计费模式分层：稳态用包年包月/RI/节省计划，弹性用按量/Spot，突发 Serverless
- 存储生命周期：热/冷/归档分层自动沉降
- 成本可见性：费用标签 + 分账（财务单元/Cost Allocation Tag）+ 预算告警
- 建立优化闭环：周报 → 责任人认领 → 优化动作验证（FinOps 运营）

**代表性服务**：Cost Explorer/Budgets/CUR/Compute Savings Plans；阿里云对应费用中心（财务单元、分账账单）、预算管理、节省计划/预留实例券。

### 1.6 可持续性（Sustainability，2021 新增第六支柱）
**定义**：最小化云工作负载的环境影响（能耗与碳足迹）。

**设计原则**：理解你的影响（先量化）；可持续性最大化目标；利用率最大化（高密度部署、缩容浪费）；采用托管服务（规模化共享基础设施更高效）；最小化数据移动与存储；下游与上游的绿色策略。

**最佳实践**：区域选择纳入碳因素；实例右型与自动缩容；老旧实例迁移到新架构（Graviton/倚天能效比更高）；数据保留策略治理"只存不删"。

## 2. 阿里云 Well-Architected（卓越架构）五支柱

阿里云官方框架为五支柱：**可靠性、安全性、成本优化、性能效率、运维**（对应 AWS 的六支柱，未单列可持续性，将卓越运营译作"运维"）。

| 阿里云支柱 | 对应 AWS 支柱 | 本项目机读清单 |
|---|---|---|
| 可靠性 REL | Reliability | REL-01~05（跨 AZ、健康检查、RPO/RTO、演练、降级熔断） |
| 安全性 SEC | Security | SEC-01~05（最小权限、边界防护、加密、审计、补丁） |
| 成本优化 COST | Cost Optimization | COST-01~05（规格匹配、计费模式、存储分层、可见性、弹性） |
| 性能效率 PERF | Performance Efficiency | PERF-01~05（容量模型、缓存、读写分离、异步、压测） |
| 运维 OPS | Operational Excellence | OPS-01~05（IaC、CI/CD、可观测、on-call、复盘） |

评审操作规程（打分、evidence、fail 项处置）见 `aliyun-waf/SKILL.md`。

## 3. WAF 评审方法论（怎么用）

### 流程
1. **圈定 Workload**：一个业务系统为单元（不是整个公司），确定业务上下文（可用性目标、合规要求、数据敏感级）
2. **逐支柱问卷**：每支柱一组问题，回答当前实现 vs 最佳实践差距
3. **风险分级**：差距项分为 **HRI（高风险项）/ MRI（中风险项）**——影响可用性/安全底线的是 HRI
4. **改进计划**：每项 HRI/MRI 给 owner、动作、优先级；HRI 必须有明确时限
5. **定期重审**：架构变更、大促前后、每年至少一次全量重审

### 各支柱高频评审问题（问卷起点，答不出即记风险项）

| 支柱 | 高频问题 |
|---|---|
| 可靠性 | RTO/RPO 是多少、谁定的？恢复流程演练过吗？关键组件还有单 AZ/单点吗？下游故障怎么降级？ |
| 安全 | 生产上还有长期明文 AccessKey 吗？谁能登生产机、怎么审计？日志留存多久？加密覆盖传输和静态了吗？ |
| 成本 | 这套系统上月花多少、谁认账？稳态/弹性流量占比多少（定 RI 与按量配比）？有没有预算告警？ |
| 性能 | 容量上限怎么算的？多久压测一次？热点读走什么（缓存/CDN）？数据库慢查询有监控吗？ |
| 运维 | 环境从零重建要多久？发布失败怎么回滚、多久？昨晚的告警谁处理的、多久响应？ |
| 可持续性* | 实例利用率和缩容策略？老旧实例是否已迁新架构（Graviton/倚天）？数据有保留策略吗？ |

*阿里云五支柱无独立可持续性，评审 AWS 工作负载或客户有 ESG 要求时使用。

### 实践要点
- **evidence 原则**：每项结论必须指向方案中的具体设计或缺失说明，不接受"应该没问题"
- **不要满分迷信**：成熟 Workload 通常也有 HRI/MRI 存量，评审的价值是**显性化风险 + 优先级排序**，不是一次改完美
- **业务权衡透明化**：有些"不合规项"是刻意成本/进度权衡，写进决策记录，评审时标注"accepted risk"
- **售前增值动作**：对客户存量系统做 WAF 体检（Well-Architected Review），产出风险热力图——这既是咨询切入点，也是厂商侧评审资助项目的常见形态（AWS WAP：完成指定数量支柱评审的伙伴可申请工作负载评审资助；阿里云侧对应架构评审与优化服务）

### Lenses（行业/技术场景扩展）
AWS 在六支柱之上有场景 lens：Serverless、SaaS、ML、数据分析、IoT、游戏、HPC、金融服务 FSI、流媒体、生成式 AI Lens（2023）。评审特定场景时叠加对应 lens 的问题集；阿里云侧对应白皮书按行业/场景的扩展篇章。

## 4. CAF × Landing Zone × WAF 的协同（全局图）

```
CAF 四阶段            平台层                Workload 层
评估 ──┐
动员 ──┼── CCoE ──→ Landing Zone ──→ 每个 Workload 上线前后
迁移 ──┤   组织保障   账号/网络/合规基线      WAF 评审 + HRI 整改
创新 ──┘
```

- 客户问"先做什么"：**Landing Zone 先于规模化迁移**（否则返工），WAF 评审嵌在每个迁移波次和新应用上线卡点
- 客户问"怎么衡量"：CAF 六维度成熟度（组织级）、LZ 基线符合率（平台级）、WAF 支柱得分与 HRI 存量（Workload 级）——三层指标组成治理仪表盘
