# POC 设计与验证

POC 是"用技术换信任"的主战场，也是售前最大的时间黑洞——做对是赢单杠杆，做错是免费咨询。

## 要不要做 POC

| 做 POC | 不做 POC |
|---|---|
| 客户有技术评审流程，POC 是必经环节 | 客户已被说服，POC 只是拖延（可能是竞品拖时间） |
| 关键指标存在争议，数据能一锤定音 | 标准化产品 + 成熟案例已足够背书 |
| 竞品同台，需要差异化证明 | 单纯"试试看"，无成功标准 |
| 复杂场景（大数据、AI、强性能要求） | 预算未立项、纯比价单（先推回商机分级） |

**接 POC 前的三问**：验证什么指标？结果如何影响决策？谁拍板认可结果？三问答不上来 = 不立项。

## POC 立项

- **验证目标 3-5 条可量化指标**：如"万级 QPS 下 P99 < 50ms""100TB 迁移窗口 ≤ 8 小时""成本较现状降 30%"。不可量化的目标（"看看稳不稳"）一律翻译成指标。
- **成功标准双方书面确认**：指标、测试环境、数据规模、评判方式、时间盒（2-4 周为常态）、双方投入人。这是防止"做完了客户说不算"的唯一保险。
- **范围锁定**：只验证选型关键点，不还原客户全量业务。范围蔓延（"顺便再试试这个"）按变更管理处理：加需求则延时间或砍范围，由客户选。

## POC 设计

- **选代表场景**：选客户最有共识、数据可得、且能体现差异化的场景；避开客户内部政治敏感的系统。
- **对照组**：与客户现状系统或竞品同条件对比（同数据、同机器规格折算、同测试脚本），单边数据说服力弱。
- **环境选择**：客户 ID 演练环境 / 云上沙箱 / 伙伴实验室，按数据敏感度与网络条件定；涉敏数据必须脱敏，数据合规责任提前约定。
- **客户共创**：让客户技术人员参与设计测试用例——参与感转化为方案认同感，测试结果由客户自己跑出来的最有说服力。

## 执行纪律

- **节奏**：开工会对齐目标与分工 → 周报同步进度与风险 → 临近验收切日报。
- **每日检查三件事**：进度 vs 计划、指标趋势、客户参与度（客户工程师突然不参与了是危险信号，立即上报 BD）。
- **留痕**：测试脚本、原始数据、环境配置全部归档——答辩和复盘的弹药。
- **故障处理**：POC 中出故障不掩盖，展示定位与解决过程反而建立信任；但要在开工时约定"故障不算失败，修复速度也是指标"。

## 结果转化

**POC 报告结构**：目标回顾 → 测试方法与环境 → 结果 vs 成功标准（逐条打勾/差距）→ 发现的问题与对策 → 生产化建议（容量规划、架构差异、实施路径）→ 结论。

- **达标**：48 小时内出报告（趁热），BD 接力把数据转成商务推进力；报告同步给客户拍板人而非只给接口人。
- **部分达标**：差距项给出根因与优化路径（参数调优/规格调整/版本差异），约定复测窗口——不硬拗结论，专业态度比单次结果更值钱。
- **不达标**：诚实止损，转向替代方案（换产品/换架构）或退出；硬赢一个 POC 输掉的是交付期和续费。

**常见坑**：无书面成功标准（最大坑）；竞品同台但对比规则未约定（对方用优化过的集群打你默认配置）；客户数据合规未约定（脱敏、留存、销毁）；POC 环境直接转生产（欠下的架构债交付期还）。

## 关键话术

- POC 是共同验证不是单方表演：目标、标准、时间盒三方确认后再开工。
- 让客户工程师亲手跑出结果：他自己说服自己。
- POC 报告的终点是生产化建议：从"测过了"直接推到"怎么上生产"，赢单后方案已写好一半。
