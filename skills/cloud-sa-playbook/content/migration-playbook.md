# 迁移上云 Playbook

售中最重的交付型商机：迁移方案的可信度直接决定赢单，迁移的成败直接决定续费。顶层设计（Landing Zone、多账号治理）深度知识见 `cloud-frameworks` 技能的 `content/aliyun-landing-zone.md`，评估阶段的交付流程见 `sa-playbooks` 技能的 `content/cloud-assessment.md`；本篇讲 SA 怎么打迁移单。

## 迁移商机全流程

    评估（发现 → 依赖分析 → TCO）→ 规划（6R 分流 → 波次设计）→ 执行（割接）→ 优化（30/60/90 天）

| 阶段 | SA 主导产出 |
|---|---|
| 评估 | 应用/中间件/数据库清单与依赖图、资源画像（利用率）、迁移 TCO 对比、风险清单 |
| 规划 | 6R 策略分配表、波次计划、网络与账号规划、目标架构蓝图 |
| 执行 | 割接方案（窗口、步骤、回滚）、验证清单、值守安排 |
| 优化 | 上云后成本与架构优化路线（转包年、降配、托管化） |

**评估要点**：依赖分析是迁移方案的命门——应用间调用、数据库主从、DNS/证书、与外部机构的专线依赖；漏一条依赖就是割接夜的一次事故。资源画像用真实监控数据（CPU/内存/IO 利用率），按峰值 P95 定目标规格，防止"原样搬运"放大成本。

## 6R 策略分流

| 策略 | 适用 | 决策依据 |
|---|---|---|
| Rehost（重托管，直接搬） | 老旧但稳定、业务不允许动 | 最快最省事，先上云再优化 |
| Replatform（小改造） | 换托管服务：自建 MySQL → RDS、自建 MQ → 消息队列 | 收益/风险比最优，主流选择 |
| Repurchase（换购 SaaS） | 邮件、CRM、协作等标准软件 | 不迁移代码，换订阅 |
| Refactor（重构/云原生） | 核心应用、需要弹性/微服务化 | 收益最大、成本风险最高，只给高价值应用 |
| Retire（下线） | 无流量僵尸系统 | 评估清单里通常 10-20% 可直接退役，直接省成本 |
| Retain（保留） | 强合规驻留、近期将替换、延迟敏感 | 写明保留理由与复审时间，避免"为什么这个没迁"的追问 |

**分流原则**：按"业务价值 × 改造成本"四象限分；第一波一定选低风险系统练手（外围/办公/测试系统），建立客户信心后再进核心。

## 波次规划

- **典型波次**：W1 试点（1-2 个低风险系统，全流程演练）→ W2 外围系统批量搬 → W3 数据库与中间件 → W4 核心交易系统（灰度/双跑）→ W5 收尾退役。
- **每波之间留观察期**（1-2 周），上一波的稳定性数据是下一波的放行条件。
- **前置项先行**：账号与权限体系、网络（专线/VPN、网段规划、DNS）、安全基线（WAF/堡垒机/日志审计）必须在 W1 前就绪——这也是 Landing Zone 先行的原因（设计模板见 `cloud-frameworks` 包）。

## 割接与回滚

- **割接窗口**：选业务低峰（周末/凌晨），倒排到分钟级的 runbook（步骤、执行人、预期耗时、验证命令）；DNS/TTL 提前调低。
- **数据同步**：全量迁移 + 增量同步（DTS 类工具）双轨，割接时只切增量尾巴，把停机窗口压到分钟级。
- **验证清单**：功能冒烟用例、核心交易链路、性能基线对比、监控与告警生效、备份任务正常。
- **回滚预案**：明确回滚触发条件（如关键验证失败、核心链路异常超 N 分钟）、决策人（当场谁拍板）、回滚时限（数据反向同步窗口内可行）；"回滚是一次正常预案，不是失败"——事先和客户达成共识，割接夜才不会赌。
- **双跑/灰度**：核心交易系统用双写双跑或按流量比例灰度，观察期达标再全量。

## 数据库迁移专项

数据库是迁移工作量与风险的最大头（信创替换同理，见 `industry-compliance.md`），应单独立项管理：

- **路径选择**：自建 MySQL/PostgreSQL → 云 RDS（兼容性最高，放第一波）；Oracle/SQL Server → 云原生数据库（兼容语法型，如 PolarDB 路线）或开源库重构（改造量最大，单独排期）；分库分表中间件 → 云原生分布式数据库。
- **同步双轨**：全量 DTS + 增量同步，割接只切增量尾巴；金融级场景用双向同步保住回退窗口。
- **验证专项**：SQL 兼容性扫描（方言/函数/存储过程）先行于一切迁移动作；数据一致性校验（行数/抽样/校验值三选二以上）；性能基线对比，慢查询清单提前治理。
- **回退设计**：回退窗口 = 双向同步可维持时长；应用连接串切换走配置中心/DNS 一次到位，禁止"改代码回退"——那是割接夜的二次事故。

## 上云后 30/60/90 天

| 时点 | 动作 | 目的 |
|---|---|---|
| 30 天 | 稳定性巡检、监控补齐、故障复盘 | 兑现"上云更稳"的承诺 |
| 60 天 | 成本优化第一轮：转包年/节省计划、降配闲置资源、存储分层 | 交出省钱的账，把 TCO 承诺变成真金白银 |
| 90 天 | Replatform 深化（托管化、Serverless 化）与新场景规划（灾备/AI/数据） | 从交付转经营，埋 Upsell 点（衔接 `account-deepening.md`） |

## 关键话术

- 迁移方案的专业度体现在依赖图和回滚预案：客户敢让你割接，是因为你把最坏情况想清楚了。
- 6R 不是技术分类是商务分类：Refactor 的单子才需要 SA 深度投入，Rehost 批量单靠标准化流水线。
- 灯塔波次：第一波成功的迁移故事，就是这个客户后续所有扩容的信用凭证。
