# 需求澄清与方案设计

售前转化的核心环节：需求澄清决定方案打不打得中，方案质量决定技术分和信任度。

## 需求澄清框架

**四层澄清**，从业务往下钻到验收标准，缺一层方案就悬空：

| 层 | 问什么 | 典型问题 |
|---|---|---|
| 业务目标 | 客户要什么业务结果 | 降本多少？支撑什么新业务？合规红线是什么？ |
| 技术需求 | 支撑目标要什么能力 | 性能/容量/可用性指标？现有架构与依赖？数据分布？ |
| 约束条件 | 什么在限制选择 | 预算、时间窗、合规（等保/数据驻留）、团队技能栈、既有供应商绑定 |
| 成功标准 | 怎么算成 | 可量化验收指标（延迟、成本、迁移完成定义），双方书面确认 |

**提问方法**：

- 用 SPIN 展开：现状（Situation）→ 痛点（Problem）→ 影响（Implication）→ 价值确认（Need-payoff）。先让客户自己说出痛点的代价，方案才有锚点。
- 区分 Must / Should / Could：Must 项决定方案骨架，全部满足才可投；Could 项是商务弹性空间。
- 警惕"伪需求"：客户要的是"更快的马"还是"更快到达"？追问业务场景而非指定产品（客户点名产品时，验证底层需求后可给更优替代）。
- 摸清非功能需求：很多丢单输在没问——数据主权要求、既有监控/运维体系、灾备 RTO/RPO 指标、团队运维能力（决定托管服务 vs 自管选型）。

## 方案文档标准结构

```
1. 背景与目标（业务语言，决策人看得懂）
2. 现状与痛点分析（引用需求澄清结论，让客户"被理解"）
3. 总体架构（一张图定调：业务架构 → 应用架构 → 部署架构三层）
4. 分模块设计（逐个痛点对逐个设计，含高可用/安全/成本设计）
5. 实施与迁移计划（阶段、里程碑、割接窗口、回滚预案）
6. TCO 与商务建议（见下节）
7. 风险与对策（诚实列出，配缓解措施——暴露风险是专业度不是减分项）
8. 案例背书（同行业标杆 1-3 个，含可验证的效果数字）
9. 附录：选型明细、参数、容量测算依据
```

**架构图三层法**：业务架构（给领导看价值流）、应用架构（给技术负责人看模块与集成）、部署架构（给运维看资源与网络）。汇报对象不同，展开的层不同，不要一张图打天下。

**容量与选型要有依据**：规格、数量、带宽都给出测算公式（如 峰值 QPS × 单请求资源 ÷ 单机承载），评审时经得起追问，也防止过度配置抬高报价丢单。

## TCO 与 ROI 测算

**上云 vs 自建 IDC 的 TCO 对比要素**：

| 成本项 | 自建 IDC | 云上 |
|---|---|---|
| 硬件 | 一次性采购 + 3-5 年折旧 | 按量/包年，随用随扩 |
| 机房与电力 | 建设或租赁、PUE 损耗 | 含在服务价格内 |
| 运维人力 | 硬件/网络/系统多层运维 | 平台层由云厂承担 |
| 峰值冗余 | 按峰值常备（平时闲置） | 弹性伸缩，峰值付费 |
| 机会成本 | 采购周期 1-3 个月起 | 分钟级开通 |

测算纪律：对比周期对齐（3 年或 5 年）；云上成本用真实账单/官网价，不用拍脑袋折扣；把人力与停机成本算进去（这是云的传统优势项，不算是账就输）。

**云内成本设计**（方案里主动写，体现专业）：稳态负载包年包月/节省计划，弹性负载按量 + 自动伸缩，存储生命周期分层，可观测先行埋成本标签。交付级优化流程见 `sa-playbooks` 技能的 `content/cost-optimization.md`。

**ROI 三种论证口径**：降本（TCO 节约额）、增效（业务增益：转化率、发布效率、新业务上市时间）、避险（合规与业务连续性——给领导层算事故期望损失）。

## 汇报与讲标式表达

- 金字塔结构：结论先行（"我们建议……三个理由"），客户时间不够时 3 分钟能讲完主干。
- 面向决策人讲价值与风险，面向技术评审讲架构与依据——同一方案两版讲法。
- 用客户的语言和数字说话：把"高可用 99.95%"翻译成"全年不可用 ≤ 4.4 小时，对你们双 11 场景意味着……"。
- Demo 是最强说服力：能用 5 分钟演示跑通的，不画 50 页 PPT。

## 产出物与关键话术

- 产出物：需求澄清纪要（含 Must/Should/Could 与成功标准）、方案建议书、TCO 对比表、汇报 PPT。
- 先诊断后开方：没做需求澄清就出方案 = 免费劳动 + 大概率打不中。
- 方案的成功标准要双方签字确认：验收扯皮是售后最大雷区。
- 报价留空间：高配/低配两版方案，让 BD 有商务弹性，客户有选择题而不是判断题。
